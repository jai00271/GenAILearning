Python for GenAI

Track: FOUND Labs: genai-gurukul-labs/found-101/ Prereq: basic Python comfort

GenAI ka saara production stack, practically bolu toh, Python pe khada hai. Model call karna ho, embedding nikaalna ho, schema validate karna ho, ya parallel API hits fire karne hon — agar aapka Python setup fragile hai, toh baaki saari “AI magic” bhi fragile lagti hai. Is module ka kaam fancy frameworks sikhana nahi hai. Kaam yeh hai ki aap woh teen engineering muscles strong kar lo jo har GenAI project mein baar-baar aati hain: isolated environments, vector math with NumPy, aur async I/O + typed schemas.

Socho jaise aap kisi naye laptop pe pehli baar project clone kar rahe ho. Agar dependencies globally mix ho gayi, kal koi model SDK update aaya aur aapka RAG script toot gaya. Agar aap cosine similarity “approximately” calculate karte ho, retrieval ranking silently galat ho sakti hai. Aur agar aap sequential awaits se 20 tool calls chalaate ho, latency bill aur user wait dono badhte hain. Yeh chapter unhi pitfalls ko pehle se sterilize karta hai.

1. Virtual environments aur dependency hygiene

Python ka default temptation yeh hai ki aap pip install seedha system Python pe maar do. Short term mein yeh tez lagta hai; long term mein yeh dependency hell banata hai. GenAI projects mein libraries tez evolve karti hain — OpenAI SDK, httpx, pydantic, tiktoken, vector DBs — versions drift karte rehte hain. Isliye har project ka apna venv hona chahiye: ek isolated folder jisme interpreter + packages us project ke liye locked hain.

Typical flow simple hai. Project root mein python3 -m venv .venv se environment banao, activate karo, phir pip install -r requirements.txt. Windows pe activation script alag hoti hai, macOS/Linux pe source .venv/bin/activate. Important baat yeh nahi hai ki aap command yaad rakho; important yeh hai ki aap habit banao: naya shell khola, pehle confirm karo kaunsa Python active hai (which python / python -c "import sys; print(sys.prefix)").

Source

packaging.python.org — Installing packages using pip and virtual environments — Official guide jo venv create/activate aur pip install workflow clearly document karti hai; “global install se bachke isolated env use karo” yahi canonical recommendation hai.

Pitfall

Kabhi-kabhi log sudo pip install maar dete hain “permission error” dekh ke. Yeh almost hamesha galat direction hai. Permission error usually yeh signal hai ki aap galat Python pe install kar rahe ho — venv activate karo, ya python -m pip install ... use karo taaki wohi interpreter target ho jo aap soch rahe ho.

2. NumPy vectors aur cosine similarity

GenAI mein text ko numbers mein badalte hain — embeddings. Ek embedding simply ek vector hai: fixed length ki floating-point list. “Yeh document us query se kitna milta-julta hai?” ka jawab aksar cosine similarity se aata hai. Cosine yeh measure karta hai ki do vectors ke beech angle kitna chhota hai, unki length ignore karke. Magai aur chhoti si needle dono “upar” point kar sakti hain — direction same, magnitude alag. Cosine exactly isi intuition ko math mein convert karta hai.

Formula yaad rakhne layak hai, lekin pehle intuition: cosine similarity = dot product divided by product of L2 norms. Agar dono vectors unit length pe normalize ho chuke hain, toh cosine seedha dot product ban jaata hai. Isliye production retrieval stacks pehle normalize karke inner product search karte hain — mathematically equivalent, computationally friendly. 

import numpy as np

def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:
    a = np.asarray(a, dtype=float).ravel()
    b = np.asarray(b, dtype=float).ravel()
    denom = np.linalg.norm(a) * np.linalg.norm(b)
    if denom == 0:
        return 0.0
    return float(np.dot(a, b) / denom)
Intuition

Cosine 1 matlab vectors same direction. Cosine 0 matlab orthogonal — “koi shared direction nahi”. Cosine -1 opposite direction. Text embeddings mein negative values rare-ish hote hain after training geometry, lekin mathematically possible. Zero-vector pe special-case karna zaroori hai, warna divide-by-zero se NaN leak ho ke ranking todd sakta hai.

3. asyncio: gather vs sequential awaits

LLM APIs network-bound hoti hain. Ek call 400ms–2s le sakti hai. Agar aapko 5 independent summaries chahiye aur aap await call() ko loop mein sequentially likhte ho, total time roughly sum of latencies ho jaata hai. Asyncio ka point yeh nahi hai ki CPU parallel ho; point yeh hai ki jab ek request network pe wait kar rahi ho, event loop doosri request bhej sakta hai.

asyncio.gather multiple awaitables ko concurrently schedule karta hai aur results (ya exceptions) collect karta hai. Contrast mein sequential pattern mein har await pehle khatam hota hai, tab next start. Neeche wala mental model yaad rakhna useful hai: concurrent tabhi help karta hai jab tasks mostly independent I/O wait kar rahe hon. Agar Task B ko Task A ka output chahiye, toh gather se magic nahi hoga — data dependency serialize karti hai. 

import asyncio
import time

async def fake_llm(delay: float, tag: str) -> str:
    await asyncio.sleep(delay)
    return tag

async def sequential():
    t0 = time.perf_counter()
    a = await fake_llm(0.3, "A")
    b = await fake_llm(0.3, "B")
    return a, b, time.perf_counter() - t0

async def parallel():
    t0 = time.perf_counter()
    a, b = await asyncio.gather(fake_llm(0.3, "A"), fake_llm(0.3, "B"))
    return a, b, time.perf_counter() - t0
Source

Python docs — asyncio.gather — Official reference: gather concurrently runs awaitables and returns aggregated results; return_exceptions=True se aap failures ko bhi result list mein absorb kar sakte ho.

Pitfall

Gather ke saath rate limits bhoolna common hai. Agar provider 60 RPM allow karta hai aur aap 200 coroutines ek saath fire kar do, toh thundering herd milta hai. Production mein semaphore (asyncio.Semaphore) ya explicit concurrency cap lagao.

Hands-on

Lab: async_calls.py — run_sequential aur run_gather likho jo same fake I/O helpers ko dono styles mein call karein. Tests timing shape verify karte hain, exact milliseconds nahi.

4. Pydantic se typed chat turns

GenAI apps message lists pe chalti hain: system, user, assistant, tool… Har message ke fields predictable hone chahiye. Agar aap plain dicts pe depend karte ho, typos late blow up karte hain — kabhi API edge pe, kabhi logs mein. Pydantic models runtime validation + clear errors dete hain. FOUND-101 mein hum ek minimal ChatTurn banate hain: role aur content required, optional name, aur role enum-like constraint. 

from typing import Literal
from pydantic import BaseModel, Field

class ChatTurn(BaseModel):
    role: Literal["system", "user", "assistant", "tool"]
    content: str = Field(min_length=1)
    name: str | None = None

Jab aap ChatTurn.model_validate(payload) call karte ho, invalid role ya empty content turant ValidationError deta hai. Yeh “fail fast at the boundary” principle hai — model call se pehle garbage ko rokna sasta hai, half-generated answer ke baad debug karna mehnga.

Source

Pydantic docs — Models — BaseModel, field constraints, aur validation lifecycle ka canonical explanation; GenAI request/response schemas isi pattern pe design hote hain.

Hands-on

Lab: schemas.py — ChatTurn define karo aur parse_turns likho jo dict list ko validated models mein convert kare. Invalid input pe exception bubble hone do (swallow mat karo).

Recall

Teen muscle memory items: (1) project-local venv + pinned requirements, (2) cosine = normalized direction match for embeddings, (3) gather for independent I/O, Pydantic for boundary schemas.
