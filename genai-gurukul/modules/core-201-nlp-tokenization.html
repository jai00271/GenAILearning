CORE 201 · NLP Fundamentals & Tokenization

Model words nahi padhta — tokens padhta hai. Aapka bill bhi unhi se banta hai.

Track: CORE Labs: genai-gurukul-labs/core-201/ Local · tiktoken · no paid API Prereq: FOUND 101–103

Backend engineer ke dimaag mein “string” ek pehli-class cheez hai: UTF-8 bytes, length, maybe a culture-aware collation. Language model ke dimaag mein pehli-class cheez token id hai — ek integer vocabulary ke andar. Jab aap prompt likhte ho, context window plan karte ho, chunk size choose karte ho, ya tokens-per-minute (TPM) capacity sochte ho (PROD 405), aap asal mein isi integer stream ke saath kaam kar rahe ho. Is chapter ka kaam yeh illusion todna hai ki model English “words” dekh raha hai, aur uski jagah woh machinery rakhna jo aap production mein daily use karoge: why we tokenize, how Byte Pair Encoding (BPE) and WordPiece build a vocabulary, what vocab-size trade-offs buy you, and how to measure real token counts with OpenAI’s tiktoken library.

Yeh NLP survey course nahi hai. Stemming, part-of-speech tagging, classical n-gram language models — unka historical value hai, lekin GenAI Application Engineer ke daily path pe nahi. Jo classical idea yahan zinda hai woh sirf itna hai: text ko discrete units mein todna zaroori hai kyunki neural nets fixed-size symbol tables par train hote hain. Uske baad hum seedha subword tokenization par aa jaate hain, kyunki wahi 2015–2026 ke LLMs ka default hai.

Perplexity token-level log-probabilities par define hoti hai, character-level ya word-level par nahi — jab tak aap explicitly woh unit choose na karo. Agar do models alag tokenizers use karte hain, unki perplexity numbers seedha compare mat karo. 1. Kyun tokenize — bytes se integers tak ka contract

Neural language model ek badi lookup table + matrix multiplies ka system hai. Har input position par use ek embedding vector chahiye (CORE 204 us vector semantics ko deepen karega). Embedding table ka size roughly vocab_size × embedding_dim hota hai. Agar aap har possible Unicode string ko ek row dete, table infinite hoti. Agar aap sirf “whitespace-separated English words” rakhte, to teen problems turant aati hain.

Pehli problem: open vocabulary. “ServiceNow”, “INC0042817”, “resetPasswordAsync”, aur kal ka naya product name — yeh training data mein na hon, aur model ke paas unke liye koi row nahi. Classical NLP ne iske liye an <UNK> token use kiya; production assistant mein har unknown word ko UNK banana matlab incident numbers aur API paths kho dena.

Doosri problem: morphology aur glue. English mein “password”, “passwords”, “password-reset” related hain; German compounds aur code identifiers aur bhi messy hain. Pure word vocab either explode karti hai ya related forms ko bilkul alag rows deti hai.

Teesri problem: cost and context. Context window tokens mein measure hota hai, characters mein nahi. Same 4,000-character runbook ek tokenizer mein 1,100 tokens ho sakta hai, doosre mein 1,800. Agar aap character length se “safe” budget karoge, kabhi window se bahar nikal jaoge, kabhi paise waste karoge. Tokenization isliye sirf linguistics nahi — yeh aapka metering, packing, aur truncation contract hai.

Intuition

Microservice world mein aap protobuf vs JSON choose karte ho: denser encoding, different schema evolution rules, different debugging pain. Tokenizers bhi encodings hain. Dense / clever encoding (subwords) rare words ko pieces mein tod deti hai; naive word encoding either UNK karti hai ya vocab explode. Aap “kaunsi encoding” ko product decision ki tarah treat karo, cosmetics ki tarah nahi.

2. Character, word, subword — teen incomplete answers

Character-level tokenization theoretically open vocabulary solve karti hai: har Unicode code point (ya byte) ek symbol. Practical dard: sequences lambi ho jaati hain, aur model ko spelling se meaning compose karna padta hai. “password” aath alag steps ban jaata hai. Short context windows pe yeh luxury mehngi padti hai.

Word-level tokenization human intuition se milti-julti hai, lekin upar wali teen problems (UNK, morphology, metering) production mein laut aati hain. Code aur incident IDs par yeh especially bura behave karti hai — exactly woh domain jahan aap GenAI Application Engineer ke taur par kaam karoge.

Subword tokenization beech ka raasta hai. Common words aksar ek hi token ban jaate hain. Rare or novel strings smaller pieces mein toot-te hain — kabhi syllables, kabhi morphemes, kabhi ajeeb fragments — lekin hamesha representable rehte hain bina UNK ke (byte-level BPE variants mein literally har UTF-8 byte cover hota hai). Modern LLMs isi family mein jeete hain.

3. Byte Pair Encoding (BPE) — merges jo corpus se seekhte hain

Byte Pair Encoding originally data compression ka trick tha: repeatedly replace the most frequent pair of symbols with a new symbol. Sennrich, Haddow, and Birch ne 2016 mein isi idea ko neural machine translation ke liye open-vocabulary translation tool banaya: pehle words ko characters (plus a word-boundary marker) mein todo, phir training corpus par frequent pairs ko merge karke ek fixed-size subword vocabulary banao. Decode time par merges reverse ho jaate hain aur text wapas milta hai.

Worked miniature. Maan lo aapka poora “corpus” yeh teen strings hain (spaces explicit): low, lowest, newer. Characters se start karo. Sabse frequent adjacent pair shayad l o ya e r hoga depending on counts. Har merge ek naya vocab entry banata hai — lo, phir low, phir est, aur aage. Jab aap merge list freeze kar dete ho, encoding algorithm left-to-right (ya tokenizer-specific rule se) greedy merges apply karta hai. Result: “lowest” shayad low + est ban jaaye, “lowing” jaise unseen word bhi pieces se cover ho sake.

GPT-family tokenizers BPE hi use karte hain, with an important modern twist: many operate on bytes (UTF-8) rather than Unicode characters, so any string is encodable. OpenAI’s tiktoken library exactly inhi BPE encodings ko expose karti hai — including cl100k_base (GPT-4 / GPT-3.5-turbo era) and o200k_base (GPT-4o family). Lab mein aap dono ko count karke dekoge ki same English prose ka token footprint encoding ke saath badalta hai.

Source

Rico Sennrich, Barry Haddow, and Alexandra Birch, “Neural Machine Translation of Rare Words with Subword Units,” ACL 2016 (arXiv:1508.07909), arxiv.org/abs/1508.07909. Paper kehti hai ki BPE se built subword vocabulary rare and unknown words ko smaller units mein segment karke open-vocabulary NMT allow karti hai, without needing a large word-level vocab.

4. WordPiece — similar goal, different selection rule

WordPiece bhi subword vocabulary banata hai, lekin pair selection ka criterion alag hai. BPE mostly frequency (kitni baar pair dikha) se merge choose karti hai. WordPiece, jaise Google’s Neural Machine Translation system documentation aur follow-on BERT-era tooling ne popularize kiya, likelihood-based / language-modelish scoring se choose karta hai: kaunsa merge training data ki likelihood ko sabse zyada improve kare. Surface pe results similar lagte hain — common words intact, rare words pieces — lekin same corpus par merges identical nahi hote.

Practitioner ke liye practical rule yeh hai: jo model load kiya hai, uska tokenizer use karo. BERT checkpoints WordPiece expect karte hain; GPT-4 family cl100k_base/o200k_base BPE expect karti hai; Llama family apna SentencePiece-style stack rakhti hai. Cross-wiring — GPT tokenizer se count karke Llama context budget claim karna — bilkul wahi galti hai jo aap protobuf payload ko JSON content-length se meter kar ke karte ho.

Source

Yonghui Wu et al., “Google’s Neural Machine Translation System: Bridging the Gap between Human and Machine Translation,” arXiv:1609.08144 (2016), arxiv.org/abs/1609.08144. Paper WordPiece model ko GNMT ke open-vocabulary approach ke taur par describe karti hai: words ko subword units mein segment kiya jata hai using a data-driven wordpiece vocabulary, so the system can handle rare and unseen words.

Pitfall

“Roughly 4 characters per token” ka rule of thumb English prose par kabhi-kabhi kaam karta hai, code, tables, aur non-English text par regularly fail hota hai. JSON with repeated keys, base64 blobs, aur markdown tables often worse compression dete hain (zyada tokens per character). RAG chunking APP 305 mein isliye token-aware hona chahiye, character-aware nahi.

5. Vocabulary size trade-offs — jo aap actually feel karoge

Vocab size ek capacity dial hai, free lunch nahi. Chhota vocab (say tens of thousands): embedding table chhoti, lekin average tokens-per-sentence zyada — kyunki words zyada pieces mein tootenge. Har sequence lambi, attention cost (CORE 202) zyada, aur same document context window mein kam fit hoga. Bada vocab (100k–200k+): common phrases ek token mein pack ho sakti hain, sequences short, lekin embedding matrix badi, aur rare token rows under-trained ho sakte hain agar data sparse ho.

Concrete footprint. OpenAI cookbook documents that cl100k_base GPT-4 / GPT-3.5-turbo / several embedding models ke saath mapped hai, aur o200k_base GPT-4o family ke saath. Naam khud hint karta hai: roughly 100k vs 200k-class vocabularies. Lab mein aap same IT runbook paragraph ko dono encodings se count karke dekoge. Expectation (not a universal law): newer larger-vocab encodings often use fewer tokens on the same English+code mix — which means the same context window holds more prose — but you must measure on your corpus, not blog folklore.

Knob Smaller vocab Larger vocab
Embedding table Fewer parameters at the edge More parameters; fatter load
Tokens / document Usually higher Usually lower on in-domain text
Rare IDs / code More fragmentation Less fragmentation if trained on similar data
Cross-model metering Never transferable — recount with the target encoding
Source

OpenAI Cookbook, “How to count tokens with tiktoken,” developers.openai.com/cookbook/examples/how_to_count_tokens_with_tiktoken (re-verified August 2026; perishable model↔encoding map). Cookbook kehta hai ki tiktoken OpenAI models ke liye fast BPE tokenizer hai, aur encodings jaise cl100k_base aur o200k_base specific model families se map hote hain; use tiktoken.encoding_for_model() ya get_encoding() to load them and encode() to turn text into token ids for counting.

6. tiktoken hands-on — counting is a production skill

APP 302 ke baad aap Bedrock / OpenAI / Ollama clients touch karoge. Token counting us se pehle aati hai kyunki bina iske aap prompt experiments ko meter nahi kar sakte. tiktoken local library hai — isi module ke lab mein koi cloud call nahi. Pattern yeh hai: 

import tiktoken

enc = tiktoken.get_encoding("cl100k_base")
ids = enc.encode("reset the service account password")
print(len(ids), ids)
print(enc.decode(ids))

Teen production habits abhi se:

  1. Count before you ship a system prompt. A 800-word “helpful assistant” manifesto easily burns hundreds of tokens on every call. That is a recurring cost, not a one-time doc.
  2. Count retrieval chunks in tokens, not characters. APP 305 chunking strategies tab meaningful hongi jab aap token budgets se sochoge.
  3. Chat wrappers add tokens. Raw string count ≠ messages API bill. Role headers, tool schemas, and multipart content each add overhead. Cookbook walks through message-format counting for chat models; lab ke Part B mein aap ek chhota helper likhoge jo role+content frames ko account kare (simplified — not every provider’s exact billing quirk).
Pitfall

Tokenizer ko “translate” samajhna. Decode(encode(text)) generally round-trips for these BPE encodings, lekin token boundaries meaning boundaries nahi hain. Ek token half-word ho sakta hai; ek JSON key ka quote alag token ho sakta hai. Isliye character-offset highlighting in UI ko token indexes se map karte waqt carefully test karo — off-by-one yahan user-visible bug ban-ta hai.

7. Hands-on lab

Hands-on · core-201

Repo: genai-gurukul-labs/core-201/. Convergent lab with starter/, adjacent solution/, and pytest. Dependency: tiktoken (already in root requirements.txt). No Ollama required. No paid API. Success: pytest core-201/tests -q green. Solution check: GURUKUL_LAB=solution pytest core-201/tests -q.

  1. counting.py — count_tokens(text, encoding_name) using tiktoken.get_encoding. Must support at least cl100k_base and o200k_base.
  2. compare.py — compare_encodings(text, names) → dict[str, int] returning token counts per encoding. Used to see footprint drift on the same IT runbook fixture.
  3. budget.py — fit_messages(messages, model_encoding, token_budget) that walks messages oldest-first and drops from the front (keeping the latest user turn) until the simplified chat framing fits. This is the same instinct as log shipping retention: newest evidence wins when the window is full. Framing rule is documented in the starter docstring (role + content + fixed per-message overhead) — match it exactly so tests stay deterministic.
  4. toy_bpe.py — a teaching-scale BPE trainer: given a list of whitespace-separated corpus words and num_merges, learn merges and encode a word into symbols. Not production tiktoken — this exists so BPE is not a black box when you explain it in an interview.

Deliverable: green tests, plus (for yourself) a three-line note: which encoding produced fewer tokens on the fixture runbook, and whether you’d still refuse to hardcode that ratio into a cost model without re-measuring on your corpus. Formative habit, not a track-challenge rubric.

Self-check · formative only

Yeh recognition check hai. Course ki rigor track challenges aur capstone acceptance se aati hai.

1. Word-level vocabulary production IT text par kyun toot-ti hai, aur subword iska kaunsa hissa fix karta hai?

Reveal answer

Incident IDs, code identifiers, and new product names are open-vocabulary; word tables need UNK or explode. Subword (BPE/WordPiece) represents unseen strings as pieces without UNK (byte-level BPE covers any UTF-8), at the cost of fragmentation and encoding-specific metering.

2. BPE training mein “merge” ka selection roughly kis cheez par hota hai, aur inference time par kya freeze hota hai?

Reveal answer

Training repeatedly merges the most frequent symbol pair (classic BPE) into a new vocab entry. Inference uses the frozen merge list / encoding — your app selects cl100k_base or similar; it does not re-learn merges per request.

3. Aap GPT-4o ke liye token budget cl100k_base se count karke kyun nahi final karenge?

Reveal answer

Model↔encoding maps differ (cookbook: GPT-4o family → o200k_base). Counts are not portable across encodings. Always recount with the target model’s encoding; treat “4 chars/token” as folklore, not a budget.
