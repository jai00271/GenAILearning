1. Function calling — model text nahi, structured action maangta hai

Classic chat: assistant string. Tool-capable turn: model JSON-ish tool_calls[] emit karta hai — name + arguments (schema-validated). Runtime tool execute karti hai, result role=tool message mein wapas jata hai, model phir final text (ya aur calls) deta hai. Yehi OpenAI / Anthropic / Ollama tool APIs ka shared shape hai; names thode alag, idea same.

  • Schema pehle — arguments JSON Schema se validate; “jo string aayi” pe eval mat chalao.
  • Idempotency / side effects — ticket update ≠ calculator; permissions tool description + server policy dono pe.
  • Retrieval as tool — APP 306 wala search ab agent ke toolbox mein; forgotten tenant filter ab agent leak surface hai.

2. MCP — tool interop ka primary contract

MCP tools specification servers ko yeh expose karne deti hai:

  1. tools/list — client ko descriptors milte hain: name, description, inputSchema (JSON Schema).
  2. tools/call — { "name": "…", "arguments": {…} } se execute; result structured content.

Lab ka ToolDescriptor.to_mcp_dict() isi shape ko mirror karta hai (inputSchema key). ToyMCPClient.list_tools / call_tool in-process stand-in hain — network transport nahi, lekin contract wahi hai jo hosts (Cursor, Claude Desktop, custom gateways) expect karte hain. Production mein MCP server alag process / remote ho sakta hai; agent loop phir bhi list → plan → call → observe.

Sources · MCP primary (verify current)

Spec tools chapter: modelcontextprotocol.io/specification/…/server/tools — tools/list, tools/call, Tool schema. Learn page: server concepts. Lab toy client; real SDK/transport alag modules / PROD track mein.

3. ReAct + planning loops — pattern, not product name

ReAct (Reason + Act): model interleaved reasoning aur actions produce karta hai; environment observation wapas context mein aati hai. Practical implementation aksar “hidden thought” + explicit tool_calls hoti hai — lab run_react har LLM completion ko ek step maanti hai.

Planning variants (plan-then-execute, scratchpads, multi-hop) sab same risk share karte hain: loop unbounded ho sakta hai. Isliye max-steps / budget / kill-switch design ka hissa hain, afterthought nahi. Debug Lab B isi failure ko cost incident ke roop mein dikhati hai → PROD 404.

Intuition · .NET / backend framing

Socho agent ≈ state machine with an LLM as the transition oracle. Tools ≈ injected ports (calculator, ITSM client, vector search). MCP descriptors ≈ OpenAPI-ish operation list the oracle is allowed to see. Circuit breaker ≈ max_steps / budget — without it you have a recursive bill generator.

4. Error handling inside the loop

Tool miss, bad args, unknown tool, LLM exception — loop crash karna usually galat default hai. Prefer:

  • Structured tool errors — {"ok": false, "error": "not_found"} — model observe karke recover kar sake.
  • Trajectory error steps — eval / ops ko dikhe ki kaunsi call fail hui.
  • Hard halt — LLM transport down, auth revoked, ya policy deny — halted=True + reason.
  • Max-steps breaker — “ek aur verify” addiction se pehle kaato.
Pitfall · “final answer dikha toh agent theek hai”

Model confidently galat ticket status de sakta hai, ya 40 unnecessary tool calls ke baad sahi number. Answer string RAG-style Recall se score mat karo. Trajectory / tool-call logs pehle class metrics hain; rubrics + online eval PROD 401.

5. Eval beat — trajectory logging (not Recall@k alone)

APP 304 ke teen boxes agents pe reuse, lekin metrics badlo:

  1. Metric: task success (final answer correct?) plus trajectory shape — tool names called, error rate, steps_used, hit_max_steps. Helper: summarize_trajectory.
  2. Data: scripted FakeLLM scenarios (calc, ticket, unknown tool, infinite tool_calls).
  3. Pass / fail: happy path ends with final; breaker sets halted; tool errors logged without crash. Full production methodology (graders, traces, online shadow) → PROD 401.

LangChain / LlamaIndex agents yahi logs differently name karte hain (callbacks, traces); discipline same: score the path, not only the paragraph.

Self-check · formative only

1. MCP tools/list response mein tool ke teen core fields?

Reveal answer

name, description, aur JSON Schema inputSchema (lab: ToolDescriptor / to_mcp_dict). Primary source: MCP tools specification.

2. ReAct loop mein max-steps circuit breaker kyun mandatory hai?

Reveal answer

Model baar-baar tool_calls maang sakta hai (“verify again”). Bina ceiling ke latency + cost unbounded — Debug B. Lab halted + halt_reason="max_steps".

3. Agents ko sirf RAG Recall@k se score kyun nahi karte?

Reveal answer

Agent success path-dependent hai: kaunse tools, kitni steps, errors, side effects. Trajectory / tool-call logs chahiye; full methodology PROD 401.

4. LangChain tool-calling vs MCP — relationship?

Reveal answer

LangChain ek application framework / implementation path hai. MCP tool discovery + call ka interop protocol hai. Is module mein MCP contract pehle; frameworks optional adapters.

5. Tool not_found pe loop crash vs structured error — prefer?

Reveal answer

Structured error + trajectory error step; model recover / user ko miss bata sake. Crash sirf unrecoverable transport/policy pe. Lab ticket miss isi pattern pe hai.
