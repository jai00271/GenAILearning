1. Pehle portfolio options — 2–3 concrete pitches

Capstone start karne se pehle product choose karo, framework nahi. Neeche teen ops/enterprise pitches hain — har ek one-line. Aap Option B/C defend kar sakte ho, lekin course default Option A hai taaki scaffold, golden template, aur acceptance table align rahein.

Option One-line pitch
A · Ops Incident Copilot (default) Runbooks + tickets + alert pages se retrieve karke on-call ko next-safe-step suggest kare — citations, halt, aur cost/latency budgets ke saath.
B · Ops runbook + ticket copilot ITSM tickets ko runbook passages se ground karke draft replies / checklists generate kare — queue triage ke liye, full auto-remediation nahi.
C · ServiceNow-style workflow agent Change/incident workflow forms pe tool-calling agent: state transitions + allowlisted actions, human approval gates ke bahar side-effects nahi.

Related flavor (optional stretch): observability incident copilot — metrics/log summaries + runbook retrieval. Agar A choose karte ho to yahi atmosphere default scaffold cover karta hai (alerts + runbooks + tickets).

Select · Option A

Default build = Ops Incident Copilot. Scaffold genai-gurukul-labs/capstone/ isi option ke against likha gaya hai: multi-format corpus stubs, FastAPI prod stubs, ≥40 golden template, writeup templates. Option B/C tabhi le jab aap acceptance table ko map karke same bar clear karo — bar kam mat karo.

2. Acceptance criteria (PRD table) — yahi pass/fail hai

Neeche wali table English deliverable bhi hai — README mein copy/paste karke apne measured values bharo. Numbers defendable hone chahiye; vibes nahi.

Criterion Bar (must clear) Evidence
Scale / corpus Multi-source ops corpus; ≥3 formats (e.g. Markdown runbook, JSON ticket, HTML alert). Fixtures may be small; README must instruct how to expand toward production scale (target narrative: ~10k+ chunks / multi-service). Corpus tree + expand instructions; ingestion notes
Latency Declare path + hardware. TTFT p95 and total end-to-end p95 measured on a frozen query sample (state both numbers and method). Latency section in eval report or README appendix
Cost model Written $ / 1k queries (or equivalent) with token, retrieval, and failover-path assumptions — not a screenshot of a single bill. writeups/cost_model.md
Eval Golden set ≥ 40 Q&A (labeled). Retrieval quality: Recall@5 ≥ 0.60 on frozen labels. Protocol (k, labeling) stated. eval/ + writeups/eval_report.md
Prod features Wired stubs (or real impl): auth header check, tracing, rate limit, failover (secondary path when primary LLM/retriever fails). app/ + architecture notes
English deliverables Eval report; cost model; failure-mode writeup covering indirect injection and cost blowup; README + architecture. writeups/ + root README
Fails acceptance

Generic “chat with docs on Lambda” (or Bedrock/API Gateway clone) without the table above — no golden≥40, no Recall@5 bar, no cost model, no failure-mode writeup, no auth/trace/rate-limit/failover story — fail. Framework logo ≠ production system.

3. Option A architecture — Ops Incident Copilot

On-call query aata hai → auth + rate limit → retrieve across runbooks/tickets/alerts → agent (optional tool loop) drafts next steps with citations → tracing har hop pe → primary path fail hone pe failover stub. Eval offline golden pe; cost model assumptions freeze.

5. Failure modes jo likhne hi padenge

writeups/failure_modes.md template mein do pehle-class stories hain:

  1. Indirect prompt injection — poisoned runbook/ticket chunk retrieve hota hai; model tool ya policy todne ki koshish karta hai (PROD 403 lineage).
  2. Cost blowup — unbounded agent loops, giant context, or failover storm → $/query explode. Caps, budgets, aur kill-switches dikhao.
