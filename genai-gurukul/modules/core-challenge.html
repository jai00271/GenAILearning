Recall · CORE 204

Embeddings dense vectors hain jo semantic neighborhood encode karte hain. Cosine / dot-product retrieval us neighborhood pe chalti hai. Model change karna matlab geometry change karna — same corpus pe do models alag neighbors, alag failure modes, alag cost/latency denge. Challenge us difference ko number + prose mein pakadna hai.

1. Challenge kya hai — aur kya nahi

Aap kam se kam do embedding models (ya compatible embedding endpoints) choose karoge — local Ollama models, sentence-transformers, ya labeled cloud APIs with a free/local fallback. Unhe ek chhote domain corpus pe chalayoge. Retrieval-style evaluation design karoge: queries vs relevant docs, ranking metrics (jaise Recall@k, MRR, ya nDCG@k — jo aap defend kar sako), plus practical knobs: embedding dimension, throughput, and roughly what it would cost at your expected document volume. Phir English mein ek one-page memo likhoge: recommendation, evidence, aur jab aap doosra model pick karte.

Yeh RAG pipeline build nahi hai — woh APP 305 ka kaam hai. Yeh fine-tune bhi nahi hai. Yeh “Hugging Face leaderboard screenshot paste” bhi nahi hai. Agar aapne domain queries ke bina sirf MTEB numbers copy kiye, Evaluation evidence dimension pe aap fail karoge. Agar metrics table hai lekin memo missing hai, Correctness/artifact pe fail. Rubric chaar axes pe 1–4 score karti hai; pass rule neeche English block mein hai.

2. Kaise approach karo — engineer ka loop

Pehle corpus freeze karo aur queries likho jo real operator language use karti hon — “auth pod CrashLoopBackOff ke baad kya check karun” jaisi, keyword dump nahi. Har query ke liye relevant document ids annotate karo (even a tiny qrels set of 8–15 queries enough hai is scale pe). Phir Model A embed → retrieve → score; Model B same queries pe. Fairness ke liye same chunking, same top-k, same preprocessing. Agar ek model 768-d hai aur doosra 384-d, dimension ko metrics table mein likho — hide mat karo.

Pitfall: leaderboard pe jo model #1 hai woh aapke runbooks pe #1 nahi ho sakta. Domain jargon (“PDB”, “HPA”, “runbook”) pe general web models soft pad sakte hain. Doosra pitfall: sirf cosine heatmap dekh ke “achha lag raha hai” bolna — woh Evaluation evidence nahi hai. Teesra: memo mein sirf winner declare karna without saying when you would reverse the call (cost spike, air-gapped deploy, multilingual ops docs).

Pitfall

Cloud embedding API use karo to cost aur data-residency ek line mein memo mein aani chahiye. Agar aapne paid API chalaya aur local fallback measure nahi kiya, Production awareness weak padegi — course ka default bias local-first hai jab tak lesson explicitly paid na kahe.

3. Portfolio-facing English — deliverables

Neeche ke boxes deliberately English mein hain. Challenge memo aur rubric criteria portfolio artifacts hain; Hinglish lesson framing unki jagah nahi leti. Hiring manager ko yeh sections aise milne chahiye jaise aapne job pe likha ho.

Portfolio-facing English · Decision memo requirements

Write a one-page decision memo (approximately 400–600 words) in clear English. State which embedding model you recommend for an IT-ops / runbook retrieval prototype and why. Include a compact metrics table comparing at least two models on the same corpus and query set (retrieval quality at a stated k, plus at least one systems metric such as latency, throughput, dimension, or estimated cost at a stated document volume). Name your evaluation protocol so a reviewer could reproduce the ranking. Call out failure cases you observed (queries where the winner still missed). End with an explicit reverse condition: when you would pick the other model instead. Do not submit starter scaffolding — there is none — and do not expect a reference solution folder.

Portfolio-facing English · Suggested corpus & models

Domain: short IT operations documents — incident runbooks, on-call notes, and service health snippets. Optional fixtures ship under genai-gurukul-labs/challenges/core/corpus/. Model pairs that work well locally include two different sentence-transformer checkpoints, or a local Ollama embedding model versus another local embedder. Cloud APIs are allowed if labeled and compared fairly against a local option. Keep the corpus small enough to embed repeatedly while you debug the evaluation loop.

4. Rubric — score yourself before APP

Yeh CORE track ka gate hai. Neeche full rubric table hai — har cell full sentences mein, taaki aap self-grade kar sako bina mentor ke. Pass rule English block mein locked hai.

Portfolio-facing English · Pass rule

Each dimension is scored from 1 to 4. You pass the CORE track challenge only when no dimension is below 2 and the average across the four dimensions is at least 3.0. Anything less means revise the artifact before treating APP 301 as unlocked for yourself.

Dimension 1 — Inadequate 2 — Developing 3 — Solid 4 — Exemplary
Correctness / artifact Deliverables are missing, not in English, or do not compare two real embedding setups on a stated corpus. A memo and some numbers exist, but the comparison is incomplete, hard to parse, or mixes incompatible setups without disclosure. A one-page English memo plus a readable metrics table compare ≥2 embedding models on the same domain corpus with clear recommendation. Artifacts are crisp, reproducible, and would be credible in a design review; tables and memo align without hand-waving.
Evaluation evidence Claims rely on vibes, marketing pages, or unrelated leaderboard screenshots with no domain queries. Some retrieval or similarity numbers appear, but the protocol (queries, relevance, k, metric definition) is vague or unreproducible. A small labeled query set and stated metrics (for example Recall@k or MRR) support the recommendation on this corpus. Evidence includes honest misses, sensitivity to k or preprocessing, and enough detail that a peer could re-run the comparison.
Engineering judgment Picks a winner without trade-offs, or optimizes a vanity metric that does not match the retrieval job. Notes a trade-off superficially but does not connect model choice to the IT-ops retrieval use case. Weighs quality against practical constraints (dimension, speed, operational fit) and states when the other model wins. Judgment reads like production triage: clear default, explicit reverse conditions, and scoped next experiments.
Production awareness Ignores cost, latency, data residency, dependency risk, or local-vs-cloud implications entirely. Mentions one production concern in passing without tying it to the recommendation. Addresses cost and/or latency and at least one operational concern (vendor lock-in, offline/air-gapped needs, or PII in ops text). Treats embedding choice as a deployable decision: capacity, failure modes, and monitoring or re-evaluation triggers are named.

Definition of Done — CORE challenge

  • ≥2 embedding models compared on one domain corpus (IT ops / runbooks OK)
  • Metrics table with retrieval quality + at least one systems metric
  • One-page decision memo in English (portfolio-facing)
  • Self-score on all four rubric dimensions; pass rule met (no dim < 2, avg ≥ 3)
  • No reliance on a starter/ or solution/ folder — none ship for this gate
