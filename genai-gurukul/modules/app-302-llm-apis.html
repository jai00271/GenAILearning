1. Thin interface — complete + stream_tokens

Lab exactly yahi pattern Python mein rakhti hai — Protocol + adapters. Business code messages list pass kare; provider-specific JSON adapters ke andar rahe.

Intuition

2. OpenAI SDK — chat + streaming

OpenAI Python SDK chat completions (aur newer Responses API) expose karti hai. Classic pattern: client.chat.completions.create(model=..., messages=..., stream=True|False). Non-stream pe aapko ek full assistant message milta hai; stream pe chunked deltas — har event mein partial content — jo aap UI pe token-by-token paint karte ho. Official streaming guide: stream flag on, phir iterate events / chunks until done.

Auth: OPENAI_API_KEY (ya project-scoped keys). Rate limits model + tier pe depend karti hain — TPM/RPM numbers perishable hain. Lab mein OpenAI adapter stub hai taaki pytest ko key na chahiye; agar aapke paas key hai to optional live path try kar sakte ho, lekin CI uspe depend nahi karti.

4. AWS Bedrock — Claude / Llama / Titan via boto3

Bedrock AWS ke andar foundation models ko API deta hai — aap data plane pe bedrock-runtime client se invoke karte ho. Do important shapes:

  • Converse / ConverseStream — unified messages API across models that support chat-style turns. AWS recommends Converse jab aap multi-model conversation code likh rahe ho (Claude, Llama, aur others jo messages support karte hain).
  • InvokeModel / InvokeModelWithResponseStream — model-specific request body (JSON bytes). Titan Text aur kuch older paths yahan common hain; raw control zyada, portability kam.

Python mein typically boto3.client("bedrock-runtime", region_name=...) phir converse(modelId=..., messages=[...]). IAM role ko bedrock:InvokeModel (aur stream ke liye bedrock:InvokeModelWithResponseStream) chahiye — Converse bhi inhi permissions pe ride karta hai.

Source · Bedrock runtime

AWS, Converse API, InvokeModel, and inference prerequisites. Paraphrase: prefer Converse for a consistent messages interface across supported models; InvokeModel sends a model-specific body; calling Converse requires bedrock:InvokeModel permission (stream variants need the WithResponseStream action).

7. Inference-serving intuition (~half lesson)

SDK wrappers soft hain. Asal constraints weights + KV cache memory pe hain. Yeh section aapko daily Ollama usage ko physics se jodta hai.

7.1 Quantization — magic word nahi

Training/checkpoint aksar FP16 (16-bit float) ya BF16 weights store karta hai. Ek parameter ≈ 2 bytes. 7B params ≈ 14 GB sirf weights — aur KV cache + activations alag. Quantization weights (kabhi activations) ko kam bits mein represent karti hai: Q8 ≈ 8-bit, Q4 ≈ 4-bit, etc. Rough arithmetic lab mein bhi hai:

bytes ≈ num_params × (bits_per_param / 8)

7e9 params × 16-bit ≈ 14 GB; same model Q4 pe ≈ 3.5 GB weights. Trade-off: chhota RAM/VRAM footprint, tez disk load, lekin thoda quality loss (task-dependent). Isliye “7B on a 8 GB laptop” possible hota hai — quantized weights ki wajah se, magic ki nahi.

GGUF (GPT-Generated Unified Format) llama.cpp ecosystem ka common packaging format hai — weights + metadata ek file mein, bahut variants quantized (Q4_K_M, Q5_K_S, …). Ollama library models typically inhi quantized GGUF-style blobs ko pull karti hai. Jab aap ollama pull karte ho, aap aksar pehle se quantized artifact laa rahe ho, full FP16 checkpoint nahi.

Intuition

JPEG images ko compress karta hai; Q4 weights ko. Dono lossy ho sakte hain. Difference: yahan “pixels” neural net parameters hain — aur serving stack (llama.cpp / Ollama) un compressed weights pe matrix multiplies chalata hai, decompress-to-FP16-on-disk nahi (implementation details vary; mental model: low-bit mature hai).

7.2 KV cache — kyun long context mehnga padta hai

Autoregressive decode: har naye token pe model past tokens pe attention karta hai. Agar aap pehle ke Key/Value projections discard kar do, har step pe poora prompt dubara process karna padega. KV cache un past K/V tensors ko RAM/VRAM mein rakhta hai taaki naya token sirf incremental work kare. Cost: 2 (K aur V dono store karne hain) × sequence length × layers × heads × dim × dtype bytes — context lambi → memory up. Isliye “128K context” marketing ke peeche serving memory pressure hai, sirf training brag nahi.

7.3 vLLM-class server vs laptop Ollama

Ollama on a laptop: developer ergonomics — pull model, one process, chat API, often single-user / light concurrency, llama.cpp-class backend, quantized GGUF. Perfect for Gurukul labs aur local prototyping.

vLLM-class production server: multi-request throughput pe optimize. Continuous batching + efficient KV memory management (PagedAttention: KV ko fixed-size blocks mein page karke fragmentation kam, GPU memory better utilize). Goal: same GPU pe zyada concurrent sequences, high tokens/sec, OpenAI-compatible HTTP often. Yeh “ek student ka laptop chat” nahi — yeh shared inference cluster pattern hai.

Source · Quantization / KV / vLLM

llama.cpp / GGUF ecosystem docs and model cards describe quantized GGUF weight formats used by local runners; GGUF spec notes (format for storing tensors + metadata). vLLM PagedAttention design and the PagedAttention paper: KV cache is the dominant dynamic memory during decode; paging KV into blocks reduces fragmentation and enables higher batch throughput than naive contiguous allocation. Paraphrase carefully: Ollama ≠ vLLM; both may serve similar open weights under very different concurrency assumptions.

8. Cost / latency trade-offs across providers

Rough decision frame (numbers nahi — axes):

  • Ollama local: $0 API, privacy friendly, latency = aapka machine, quality = jo quantized model aap pull kar sakte ho, concurrency limited.
  • OpenAI / Anthropic APIs: best DX + strong models, metered $, data egress policy matter, rate limits, streaming UX polished.
  • Bedrock: AWS IAM/VPC story, multi-model (Claude/Llama/Titan) ek bill pe, region lock-in, enablement/IAM friction pehli baar, enterprise procurement path.

Latency: network RTT + queue + TTFT + decode tokens/sec. Local small Q4 model kabhi-kabhi cloud large model se “snappier” feel karta hai short prompts pe — lekin quality alag game hai. Cost estimator lab helper sirf placeholder rates se arithmetic sikhata hai; production forecast se pehle vendor pages refresh karo.

Pitfall

Streaming on kar ke bhi aap output tokens ka paisa (cloud pe) usually phir bhi dete ho — stream billing cancel nahi karta, sirf UX badalta hai. Aur local pe “free” ka matlab GPU memory pressure free nahi.

Self-check · formative only

1. Thin LLMClient interface kyun? OpenAI messages ko seedha har controller mein kyun nahi?

Reveal answer

Providers alag JSON/SDK shapes use karte hain (system field location, stream events, Bedrock modelId). Ek complete/stream_tokens contract business code ko swap-friendly banata hai; adapters isolation dete hain.

2. 7B params FP16 vs Q4 pe weight memory roughly kitni, aur Ollama se connection kya hai?

Reveal answer

FP16 ≈ 14 GB weights; Q4 ≈ 3.5 GB (params × bits/8). Ollama pulls usually GGUF quantized variants — isliye consumer laptops pe chal paate hain; “7B” name full FP16 footprint imply nahi karta.

3. August 2026 mein Bedrock pe pehli Claude call se pehle aap kya verify karoge?

Reveal answer

Region + Model Catalog/playground; Anthropic one-time use form; IAM InvokeModel (+ stream if needed); org SCPs; phir boto3 smoke converse. Purana “Request model access” UI assume mat karo — auto-enable era, lekin Anthropic form + IAM ab bhi real gates hain.

4. KV cache kya store karta hai, aur vLLM-class server Ollama laptop se kaise differ karta hai?

Reveal answer

Past tokens ke Key/Value tensors taaki decode incremental rahe. vLLM-class systems paged KV + continuous batching se multi-user GPU throughput maximize karte hain; laptop Ollama DX/local single-user (or light) quantized serving prioritize karta hai.
