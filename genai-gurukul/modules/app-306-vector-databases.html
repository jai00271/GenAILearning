1. Vector DB kya hai — .NET / backend framing

Relational instinct: table + B-tree index + WHERE. Vector store roughly: (id, vector[D], metadata JSON) + similarity operator (ORDER BY cosine(query, vec) DESC LIMIT k) + optional metadata predicate. Difference: similarity search exact SQL sort nahi — billion-scale pe Approximate Nearest Neighbor (ANN) graphs / inverted lists use hote hain. Exact scan chhote corpora pe theek; large pe latency budget tod deta hai.

  • Collection / index / namespace — logical bag of vectors (vendor names vary).
  • Upsert / delete — embedding model version change = re-embed (CORE 204 pitfall).
  • Metadata filters — tenant, locale, ACL, doc_type — product correctness yahi se aati hai.
  • Hybrid — lexical (BM25) + vector; OpenSearch natural fit; Pinecone/pgvector patterns vary.

2. Local vs managed — pick for the job, not the blog

Practitioner map (as of August 2026 — re-check vendor docs before locking SKUs):

Option Where it shines Trade-offs
Chroma (local / embedded) Prototypes, laptop RAG, pytest-friendly collections Ops / HA / multi-region not the point; treat as app-local store
FAISS (library) Fast exact / IVF / HNSW-style indexes in-process You own persistence, sharding, filters, ACL; not a full DB
Pinecone (managed; free tier for learning) Hosted ANN + metadata filters without cluster babysitting Vendor lock / cost at scale; free tier limits — check current quotas
AWS OpenSearch Serverless k-NN + lexical hybrid in AWS estate; serverless capacity units Mapping / engine choices matter; cold-start + AOSS auth model
pgvector (Postgres extension) Vectors next to relational truth; transactions, joins, RLS ANN indexes (IVFFlat / HNSW) tune karo; huge corpora pe dedicated vector DB compete

Lab default: NumPy exact index — FAISS semantics bina FAISS wheel ke. Production mein FAISS tab jab aap process-local speed chahte ho aur persistence/ACL khud own karoge. Managed tab jab team index ops nahi chahati. pgvector tab jab Postgres already source of truth hai aur RLS / tenant columns natural hain.

3. Indexing trade-offs — exact, IVF, HNSW, and rebuilds

Index type = latency ↔ recall dial (APP 304 vocabulary reuse):

  1. Exact / flat — har candidate score. Recall ceiling high; N·D badhne pe latency toot-ti hai. Lab probe_fraction=1.0 yahi hai.
  2. IVF / nprobe — space ko lists mein todo; query sirf kuch lists probe karti hai. Zyada nprobe ≈ zyada recall + zyada latency. Lab ka probe_fraction deterministic teaching stand-in hai.
  3. HNSW / graph — efSearch jaisa budget neighbors expand karta hai. Build-time M / efConstruction memory + build cost badhate hain.
  4. Rebuild / re-embed — naya embedding model, naya D, naya distance metric, ya filter cardinality explosion → plan a cutover. Mixed-model indexes silent garbage dete hain.
Intuition · SQL vs ANN

Socho IVF lists ≈ partition pruning: kam partitions scan = tez, miss risk. HNSW efSearch ≈ “kitni door graph walk”. Exact = full table scan with a fancy distance. Product decision: p95 latency SLO ke under minimum acceptable Recall@k (APP 304). Vibes se nprobe mat badhao.

4. Tenant isolation — named here, deepened in PROD 405

SaaS RAG almost always multi-tenant hai. Dangerous default: ek shared collection mein saari companies ke chunks, aur hope ki app layer filter={tenant_id} kabhi na bhule. Bhool gaye to semantic search correctly kisi aur tenant ka password-reset runbook top pe laa sakta hai — cosine “helpful” hai, authorization nahi.

Patterns (increasing hardness):

  1. Filter-enforced shared index — har query pe mandatory tenant_id (ya workspace) predicate. App bug = data leak. Lab isi failure ko tenant_isolation_bug_demo se dikhati hai.
  2. Per-tenant collection / namespace / index — blast radius chhota; ops cost / cold-start / quota zyada.
  3. Postgres RLS + pgvector — DB session tenant context; still verify vector queries RLS respect karti hain under your extension/plan.
  4. PROD 405 — tenancy, key management, audit, red-team retrieval leaks. Yahan sirf: shared collection ≠ multi-tenant-safe by itself.
Pitfall · “metadata hai toh secure hai”

Metadata field exist karna ≠ every code path filter lagati hai. Batch jobs, eval notebooks, “debug top-20”, agent tools — sab leak surface hain. Treat missing tenant filter as a security bug, not a nicety. Do not pretend filter-optional APIs are tenant-safe.

Self-check · formative only

1. Shared vector collection multi-tenant-safe kab hoti hai?

Reveal answer

Kabhi “by default” nahi. Tabhi jab har read path pe tenant (ya stronger) predicate enforce ho — ideally DB/index policy, not hope. Omitted filter = cross-tenant semantic leak. Per-tenant indexes / RLS stronger patterns; PROD 405 deepen karega.

2. FAISS library vs Pinecone managed — kab kaunsa?

Reveal answer

FAISS: in-process speed, aap persistence/ACL/ops own karte ho. Pinecone: hosted ANN + filters, less cluster toil, vendor meter/limits. Lab NumPy exact — CI bina heavy wheels.

3. nprobe / probe_fraction badhane ka expected effect?

Reveal answer

Zyada candidates score → aksar higher Recall@k, higher latency. Eval beat: measure both on a golden/fixture set; pick operating point under latency SLO.

4. pgvector kab strong default hai?

Reveal answer

Jab relational data already Postgres mein hai, transactions/joins/RLS chahiye, aur corpus size ANN indexes se handle-able hai. Ultra-large dedicated vector estates pe specialized stores compete — measure, don’t dogma.

5. AWS OpenSearch Serverless yahan kyun explicitly named?

Reveal answer

AWS-heavy teams ke liye k-NN + lexical hybrid ek familiar managed surface hai (Serverless capacity model alag from provisioned domains). Mapping/engine choices matter — primary AWS k-NN docs se verify karo.
