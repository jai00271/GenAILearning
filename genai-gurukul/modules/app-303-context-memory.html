Context window vs retrieve-later: yaad rakhna seekho — dump mat karo

Recall · CORE 201 / 203 · APP 302

Token budget characters nahi — CORE 201 framing + OpenAI tiktoken cookbook. Window size = model/API protocol limit (CORE 203). Messages array = request payload (APP 302). APP 303 = payload design: kya append karna, kab compact karna, kya retrieve-later label karna.

1. Long-context vs RAG — trade-off pehle, pipeline baad mein

Marketing slide kehti hai “1M context — sab kuch daal do.” Engineering reality alag hai. Anthropic ka context-windows guide clearly kehta hai: zyada context automatically better nahi; token count badhne se accuracy/recall degrade ho sakti hai (context rot), isliye curate karna utna hi zaroori hai jitna space. OpenAI model cards (jaise GPT-4o) context window aur max output alag list karti hain — input dump free nahi; har token latency, cost, aur attention competition hai.

Long-context stuffing tab sensible hai jab: (a) material isne turn ke liye genuinely joint reasoning maangta hai, (b) corpus chhota aur stable hai, (c) aap cost/latency accept karte ho, (d) aap empirically check karte ho ki model middle/end facts miss nahi kar raha. RAG / retrieve-later tab jab: corpus bada, frequently updated, multi-tenant, ya PII/policy se “sirf zarurat pe fetch” better hai. Hybrid common hai: short live state window mein, long docs retrieve pe.

Source · context windows (as of August 2026)

Prefer the decision framework over memorizing exact token limits — vendor numbers move. Illustrative cites: OpenAI GPT-4o model page lists a 128,000-token context window and 16,384 max output tokens (platform.openai.com/docs/models/gpt-4o). Anthropic context-windows doc: depending on model, windows are documented up to 1M tokens (e.g. newer Opus/Sonnet lines) or 200k for other Claude models; more context ≠ automatically better — curate against context rot (platform.claude.com/docs/en/build-with-claude/context-windows). Re-check vendor model pages before you hard-code budgets in production.

Intuition · .NET / backend

Socho HTTP request body vs Redis / DB. Body = abhi is request ke liye zaroori state. Side store = badi / shared / sensitive / infrequently needed data. Context window ≈ body (+ response room). RAG index ≈ queryable side store. Cache TTL intuition useful hai — “session goal 30 min sticky; live ticket status 60s stale-ok; PII never in long-lived prompt cache.” Analogy toot-ti hai: LLM non-deterministic hai, aur “body size” tokens + attention competition se measure hoti hai, JSON bytes se nahi.

2. Conversation memory & session state

Chat product mein teen layers confuse mat karo:

  1. Turn payload — jo messages list is API call mein jaati hai (APP 302).
  2. Conversation memory — multi-turn history ka managed view: raw turns + compacted summaries. Lab ka ConversationMemory yahi hai.
  3. Session / durable state — user id, open INC, preferred region, tool credentials handles — aksar Redis/DB; model ko sirf projection dikhao.

Backend mein aap session cookie + server store se yeh split pehle se jaante ho. GenAI mein extra constraint: har projection token budget khaati hai, aur summary ek lossy compress hai — galat compact = silent bug, crash nahi.

Where the analog breaks

Redis GET deterministic hai. Summarizer / model call nahi — isi liye lab FakeSummarizer injectable rakhta hai taaki pytest offline deterministic rahe. Production mein compaction ko versioned prompts + eval golden sets (APP 304) se treat karo, “kabhi kabhi theek lagta hai” se nahi. Token budgets bhi soft nahi: overflow = 400 / truncated generation, silent “ignore middle of prompt” behavior ke saath.

3. Summarization / compaction strategies

Jab history budget cross kare, common patterns:

  • Drop oldest — CORE 201 fit_messages: simple, lekin early constraints / ticket IDs kho sakte hain.
  • Summarize-then-keep-recent — purani turns → ek summary message; last N turns verbatim. Lab default yahi hai.
  • Structured state extract — “open INC, severity, last action” fields DB mein; prose history compact. Agents ke liye often best.
  • Vendor compaction / context editing — kuch APIs server-side summarize / tool-result clearing offer karti hain (Anthropic docs: compaction / context editing). Product control vs ops convenience trade-off; phir bhi aapko decide karna hai kya never summarize hona chahiye (authz decisions, raw PII).

Token accounting ke liye production mein model-matched encoding use karo. Teaching + offline tests: CORE 201 framing (per-message overhead + priming) aur OpenAI tiktoken cookbook — count tokens, don’t guess characters.

4. Window vs retrieve-later — decision table

IT ops copilot example: har item pe ek placement call. Lab decide_placement(item) → "window" | "retrieve_later" isi table ko code mein lock karta hai.

Item Default placement Why
Live ticket / INC status window Current turn reasoning; freshness high; small
Session goal / user prefs window Sticky across turns; tiny; shapes every reply
Stable runbook / wiki page retrieve_later Large, shared, versioned — fetch when relevant
PII note (employee phone, SSN fragment) retrieve_later Minimize dwell in prompts/logs; fetch under policy
Any item with sensitivity=pii retrieve_later Override — even if kind looks “live”
Heuristic, not law

Agar live ticket ke saath 40-page runbook is turn mein jointly edit/compare karna hai, short-term window stuff OK ho sakta hai — phir compact/drop. Default table pehle safe split seekhati hai; exceptions ko eval (APP 304) se justify karo.

Self-check · formative only

1. Long-context stuffing kab default mat banao, aur RAG kab?

Reveal answer

Stuffing: chhota/joint corpus, aap cost+rot accept karte ho. RAG/retrieve-later: bada, changing, multi-tenant, ya policy-sensitive material. Hybrid: live state window, docs retrieve. Window size marketing ≠ free infinite memory.

2. Session Redis vs conversation memory vs turn payload — farq?

Reveal answer

Durable session = server store (INC id, prefs). Conversation memory = managed history (raw + summaries) jo turns feed karti hai. Turn payload = is API call ki messages list. Same data teen projections ho sakti hain; tokens sirf payload pe meter hote hain.

3. Runbook, live ticket, PII note — default placements?

Reveal answer

Live ticket → window. Runbook → retrieve_later. PII note (ya koi bhi sensitivity=pii) → retrieve_later. Lab heuristic yahi encode karti hai.

4. Backend cache TTL analogy GenAI mein kahan toot-ti hai?

Reveal answer

Cache reads deterministic; summarizers/LLMs nahi. Plus hard token budgets aur attention competition — bytes fit hone ka matlab model ne fact use kiya, nahi hota. Isliye FakeSummarizer + eval, sirf TTL knobs nahi.
