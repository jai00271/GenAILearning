1. System prompt — defaults, constraints, output contract

Chat APIs usually messages ki list leti hain jisme pehla useful layer role: system hota hai (Ollama chat API bhi yeh roles support karti hai). System text model ko batata hai: tum kaun ho, kya allow hai, kya refuse karna hai, aur kab structured shape mein jawab dena hai. .NET analogy: yeh global middleware + feature flags ka mix hai — request-scoped user message se pehle apply hota hai, lekin “hard OS kernel” nahi. Model ab bhi user text ko instructions jaisa treat kar sakta hai; isliye system prompt defence ka ek hissa hai, poora security boundary nahi.

Achhi system prompt teen blocks clear rakhti hai. (1) Role / scope — “IT ops triage assistant for internal runbooks; no legal advice.” (2) Constraints — “never invent ticket IDs; if evidence missing, say so; refuse secrets.” (3) Output contract — “reply in plain prose” ya “emit one JSON object matching fields X.” Lab ka build_system_prompt inhi teen knobs ko deterministic string mein jodta hai taaki aap config diffs review kar sako jaise appsettings change.

Intuition

Feature flag socho: TriageMode=StrictJson. System prompt us flag ka human-readable form hai. Flag change karte waqt aap PR review karte ho; system prompt change pe bhi same discipline rakho — diff, owner, aur ek chhota regression set (APP 304 evaluation se pehle bhi manually).

2. Few-shot — fixtures, not essays

Zero-shot matlab sirf instruction. Few-shot matlab aap 1–N completed (user, assistant) pairs context mein daalte ho taaki model format, tone, aur edge-case handling copy kare. Backend mental model: yeh integration-test fixtures hain jo runtime pe ship ho rahe hain. Har example tokens khata hai (phir se CORE 201), isliye “das lambi stories” usually worse hai “do crisp goldens” se.

Achhi few-shot discipline: examples real distribution se aayein (happy path + ek refusal / missing-data case); assistant side wohi schema follow kare jo aap live pe expect karte ho; contradictory examples mat mix karo. Lab ka few_shot_messages system string + example pairs + final user query ko Ollama-compatible {role, content} list mein fold karta hai.

Pitfall

Few-shot mein secrets, real customer PII, ya internal URLs paste mat karo “kyunki example better lagega”. Jo context window mein gaya, woh log, cache, aur vendor retention policies ke under leak surface ban sakta hai. Synthetic tickets use karo.

3. Chain-of-thought — kab “soch ke” jawab maango

Chain-of-thought (CoT) prompting model ko intermediate reasoning steps likhne ko kehta hai — “step by step”, “pehle facts list karo, phir conclude”. Multi-hop triage, math-ish counting, ya conflicting evidence pe yeh kabhi-kabhi accuracy badhata hai. Lekin yeh free lunch nahi: zyada tokens, zyada latency, aur kabhi-kabhi confident-looking nonsense with pretty steps.

Production mapping: CoT ≈ verbose diagnostic mode. Customer-facing UI pe raw chain mat dump karo by default — sensitive reasoning leak ho sakti hai, aur users “steps” ko audited proof samajh baithe. Internal tools mein aap chain ko separate field mein rakh sakte ho, final answer alag. Yeh lesson CoT ko pattern ke tor pe introduce karta hai; deep eval APP 304.

Intuition

Socho Structured logging vs user-visible error message. CoT “debug log” hai; final answer “HTTP response body”. Dono mix karke ek hi string mein bhejna = production log ko browser mein print karna.

4. Structured output — prompt + parse + validate (Ollama lab)

Agents aur tools ko free-form prose se zyada typed objects chahiye: severity enum, booleans, short summary. Pattern jo APP 301 lab enforce karti hai: (1) system/user mein clearly bolo “return one JSON object with keys …”; (2) model se string lo; (3) markdown fences / preamble strip karke JSON extract karo; (4) Pydantic se validate — fail closed. Yeh wahi discipline hai jo aap unknown JSON ko JsonSerializer + DataAnnotations se parse karte waqt use karte ho.

Hosted providers often offer stronger knobs: JSON mode, response_format, ya schema-constrained decoding / function calling. Unka exact HTTP shape vendor-specific hai aur APP 302 mein aayega. Yahan simplification intentionally labeled hai: local Ollama pe aap pehle contract + validation seekho; constrained decoding baad mein optimization hai, replacement for validation nahi.

5. Prompt injection basics — user-typed only

Prompt injection tab hota hai jab attacker-controlled text model ko aise behave karne pe majboor kare jo developer ne intend nahi kiya — policy ignore, secrets leak, tool misuse. OWASP LLM Top 10 is risk ko LLM01: Prompt Injection ke under rakhta hai, aur direct (user types the payload) vs indirect (payload lives in external content the model later reads) forms document karta hai. APP 301 sirf direct / user-typed basics cover karti hai. Indirect / RAG-borne injection — documents, tickets, web pages ke andar hidden instructions — PROD 403 ka scope hai; yahan usko “solved” mat samjho.

Lab ka detect_simple_injection teaching-scale heuristics hai: phrases jaise “ignore previous instructions”, “reveal your system prompt”, “you are now DAN”, role-override cosplay. Yeh production WAF replacement nahi hai — false positives/negatives dono honge. Real defence-in-depth: least-privilege tools, human approval for side effects, output filtering, monitoring, aur architecture jo untrusted text ko “data” treat kare. Heuristics pehli tripwire hain, last line of defence nahi.

Source · OWASP LLM01

OWASP GenAI Security Project, “LLM01:2025 Prompt Injection”, genai.owasp.org/llmrisk/llm01-prompt-injection (see also the OWASP Top 10 for LLM Applications 2025 PDF on the OWASP project pages). Paraphrase: a prompt injection vulnerability occurs when user prompts alter the LLM’s behaviour or output in unintended ways; OWASP discusses direct and indirect forms and notes that RAG / fine-tuning alone do not fully eliminate the risk. Jailbreaking is described as related (often overlapping) behaviour where inputs push the model to disregard safety protocols. Simplification: this lesson’s detector is a didactic keyword / pattern heuristic for user-typed payloads only — not an OWASP-complete control set.

Pitfall

“System prompt mein likh diya ‘never reveal yourself’” ko airtight security mat samjho. Model instructions soft hain. Jo cheez leak nahi honi chahiye (API keys, internal URLs, customer data), use prompt mein daalo hi mat — secret store / server-side tools mein rakho.

Self-check · formative only

1. System prompt ko .NET/config mental model se kaise map karoge, aur woh mapping kahan toot-ti hai?

Reveal answer

Map: role/constraints/output contract ≈ appsettings + policy defaults applied before the user request. Breaks: unlike signed middleware, the model can still treat user text as instructions — system prompt soft policy hai, hard security boundary nahi.

2. APP 301 structured JSON lab OpenAI JSON-mode kyun require nahi karti?

Reveal answer

Kyunki portable skill prompt contract + parse + Pydantic validation hai, jo local Ollama pe FakeCompleter/OllamaCompleter se seekhi jaati hai. Provider JSON-mode / schema constraints APP 302 topic hain; validation phir bhi rakhni chahiye.

3. User-typed injection heuristics kya catch karti hain, aur RAG-borne injection kahan cover hoga?

Reveal answer

Heuristics common direct phrases detect karti hain (“ignore previous instructions”, system-prompt exfiltration asks, etc.) as a teaching tripwire — not complete prevention. Indirect / document-borne injection PROD 403 ka scope hai (OWASP LLM01 dono forms note karta hai).
