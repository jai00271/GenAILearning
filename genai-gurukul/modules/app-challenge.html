Recall · APP 304 · 305 · 307 · 308

Eval beat = metric · data · pass-fail (APP 304). RAG = retrieve then generate with citations/refusals (APP 305). Agent = tools + loop + halt + trajectory (APP 307). Multi-agent only when allowlists / parallelism justify it (APP 308). Challenge un threads ko ek portfolio artifact mein bandh'ta hai.

1. Challenge kya hai — aur kya nahi

Design a small IT-ops (or coherent domain) assistant: corpus → chunk / embed / retrieve → expose retrieval as a tool → single agent that may call that tool (and at most a tiny auxiliary tool set). Report APP 304-style metrics on a frozen query set (e.g. Recall@k / MRR / P@k — jo aap defend kar sako) plus at least one systems signal (latency, hops, or tool-error rate). Write an English trade-off memo: why single-agent, what you postponed (multi-agent, reranker, managed vector DB), and when you would reverse.

Yeh full multi-agent crew nahi hai. Yeh CAP 501 capstone nahi hai. Yeh “fine-tune the model” nahi hai. Agar aapne metrics ke bina architecture diagram paste kiya, Evaluation evidence pe fail. Agar memo missing hai, Correctness/artifact pe fail.

2. Kaise approach karo

Pehle constraints freeze karo (latency ceiling, corpus size, max tool set, local-first bias). Phir golden queries + relevance labels. Retrieval metrics APP 304 checkpoint style socho. Agent ke liye trajectory sample rakho (even if FakeLLM/scripted). Memo mein explicitly likho: multi-agent kyun nahi (ya kab haan).

3. Portfolio-facing English — deliverables

Portfolio-facing English · Trade-off memo requirements

Write a one-page trade-off memo (approximately 400–600 words) in clear English. Describe your small RAG + single-agent slice: corpus domain, retrieval tool contract, agent stop conditions, and constraints you accepted (latency, cost, local-only, max tools). Include a compact metrics table using APP 304-style measures on a stated query set (for example Recall@k or MRR, plus at least one systems metric such as p95 latency or mean tool hops). Explain why you did not default to multi-agent orchestration (or justify a narrow exception). End with reverse conditions: when you would add a second agent, change the vector store, or widen the tool catalog. Do not submit starter scaffolding — there is none — and do not expect a reference solution folder.

Portfolio-facing English · Suggested constraints

Keep the corpus small enough to re-embed while debugging. Prefer local embedders / Ollama over paid APIs unless labeled and compared. Cap the agent at a small tool set (retrieval plus at most one or two auxiliaries). Freeze max steps / hops. If you use a framework, name what you still own: tool catalog, trajectory log, and eval gates (APP 308 lock-in lesson).

4. Rubric — score yourself before PROD

Portfolio-facing English · Pass rule

Each dimension is scored from 1 to 4. You pass the APP track challenge only when no dimension is below 2 and the average across the four dimensions is at least 3.0. Anything less means revise the artifact before treating PROD 401 as unlocked for yourself.

Dimension 1 — Inadequate 2 — Developing 3 — Solid 4 — Exemplary
Correctness / artifact Deliverables are missing, not in English, or do not describe a real RAG + single-agent slice under stated constraints. A memo and some design notes exist, but the slice is vague, incomplete, or mixes incompatible setups without disclosure. A one-page English memo plus a readable metrics table describe a constrained RAG tool + single-agent design with a clear recommendation. Artifacts are crisp, reproducible, and would be credible in a design review; tables, trajectory notes, and memo align.
Evaluation evidence Claims rely on vibes, screenshots, or demos with no APP 304-style metrics on a stated query set. Some numbers appear, but the protocol (queries, relevance, k, metric definition) is vague or unreproducible. A small labeled query set and stated APP 304-style metrics (for example Recall@k or MRR) plus one systems metric support the write-up. Evidence includes honest misses, trajectory or hop observations, and enough detail that a peer could re-run the comparison.
Engineering judgment Defaults to multi-agent or a heavy framework without trade-offs, or ignores the single-agent constraint. Notes a trade-off superficially but does not connect choices to constraints and the retrieval+agent job. Weighs single-agent vs multi-agent, tool-catalog scope, and storage/retrieval choices; states when the call reverses. Judgment reads like production triage: clear default, explicit reverse conditions, scoped next experiments.
Production awareness Ignores cost, latency, halt conditions, data residency, or dependency/lock-in risk entirely. Mentions one production concern in passing without tying it to the recommendation. Addresses latency and/or cost and at least one operational concern (halt/max-steps, tool allowlists, vendor lock-in, or local-first needs). Treats the slice as deployable: failure modes, monitoring or re-eval triggers, and framework-seam ownership are named.

Definition of Done — APP challenge

  • Small RAG + single-agent slice designed under explicit constraints
  • APP 304-style metrics table (quality + ≥1 systems metric)
  • One-page English trade-off memo (portfolio-facing)
  • Self-score on all four rubric dimensions; pass rule met (no dim < 2, avg ≥ 3)
  • No reliance on a starter/ or solution/ folder — none ship for this gate
  • Gate banner: score yourself before PROD
