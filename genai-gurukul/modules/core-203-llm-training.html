CORE 203 · How LLMs Are Trained

Pretrain → SFT → preference: model “smart” hone se pehle, model “useful” banta hai

Track: CORE Labs: genai-gurukul-labs/core-203/ Local math · no paid API Prereq: CORE 202 + FOUND 102 log-probs / perplexity

CORE 202 ne dikhaya ki Transformer tokens ko kaise mix karta hai. Ab sawal training ka hai: woh weights kis loss se seekhte hain, aur chat-ready model raw next-token predictor se kitne stages door hai. Industry stack aaj teen clear phases mein padha jaata hai — pretraining (internet-scale next-token prediction), supervised fine-tuning (SFT) (instruction / demonstration data), aur preference optimization (RLHF ya DPO jaise methods jo “chosen vs rejected” answers se seekhte hain). Yeh chapter un phases ko practitioner language mein lock karta hai: aap vendor blog mein “aligned with RLHF” padho to pipeline samajh aaye, aur aap apne eval harness mein pretraining loss ko FOUND 102 ke log-probs / perplexity se jod sako.

Scope honest rakho. Hum GPU cluster schedule nahi likhenge, reward-model gradients ka full derivation nahi karenge, aur masters-level optimization theory nahi padhayenge. Jo lab mein hoga: short sequence ke token log-probs se mean NLL aur perplexity, plus ek toy DPO-style preference loss term — taaki papers ke symbols aapke Python mein concrete ho jayein.

Recall · FOUND 102

Token log-probability natural log mein measure hoti hai. Sequence ka mean negative log-likelihood (NLL) = average of −log p(token_i). Perplexity PPL = exp(mean NLL) — effective branching factor ki intuition. Pretraining loss isi family ka hai: model next token ki probability maximize karti hai, jo numerically mean NLL minimize karne ke barabar hai. Lab wahi formulas teaching scale par dubara implement karega (found-102 se import nahi — concepts reuse).

1. Pretraining — next-token negative log-likelihood

Autoregressive language model training ka contract seedha hai. Corpus se ek sequence x₁, x₂, …, xₙ lo. Position t par model, pehle ke tokens x_<t dekh kar, vocabulary par distribution p_θ(x_t | x_<t) predict karta hai. Loss us distribution ke under true token ki negative log-probability hai. Batch / sequence par average lete ho — wahi cross-entropy / mean NLL jo FOUND 102 mein aayi. Teacher forcing mein poori sequence ke targets parallel compute hote hain (CORE 202 causal mask yahi leak rokta hai).

Pretraining ka goal “chatbot banana” nahi hota. Goal hota hai: broad text distribution ko compress karna — syntax, facts jo data mein hain, patterns, code, dialogue fragments — taaki model next token predict kar sake. Quality signal often reported as validation perplexity ya bits-per-byte on held-out corpora. Lower PPL on a fixed eval set usually better next-token modeling indicate karti hai; yeh user preference ya safety ka direct measure nahi hai. Simplified label: pretrain = capability substrate; later stages = behavior shaping.

Source

Alec Radford et al., “Language Models are Unsupervised Multitask Learners” (GPT-2 technical report), OpenAI, 2019, cdn.openai.com/…/language_models_are_unsupervised_multitask_learners.pdf. Report frames the learning objective as maximizing the likelihood of the next token given previous context — unsupervised language modeling as a transferable pretraining task that can be queried with natural-language prompts without task-specific architectures.

Intuition

Datadog log pipeline socho: har event ke liye model “agla field kya hoga?” predict karti hai. Agar true field rare hai aur model ne usse low probability di, NLL high — surprise zyada. Pretraining millions of such surprises ko average karke weights update karti hai. Chat product ka “helpful answer” yahan abhi target nahi; pehle language ke statistics seekhna hai.

2. Supervised fine-tuning (SFT) — demonstrations se behavior

Raw pretrained model powerful hone ke bawajood aksar instructions ko “complete the internet” style mein treat karti hai: prompt ke baad plausible continuation, jo user ke intent se match na kare. SFT us gap ko band karti hai. Aap curated (prompt, ideal completion) pairs collect karte ho — human-written ya high-quality synthetic — aur same next-token NLL loss se model ko un completions par fine-tune karte ho. Loss function pretraining jaisi reh sakti hai; data distribution badal jaati hai: ab targets “good assistant replies” hain, random web text nahi.

Practitioner reading: SFT quality ceiling aapke demonstration set ki quality aur coverage se bound hoti hai. Agar aapke examples mein tool-use, refusal patterns, ya domain jargon missing hai, model un behaviors ko reliably nahi seekhegi. SFT ke baad bhi model kabhi-kabhi sycophantic ya verbose ho sakti hai — isliye preference stage aati hai. Simplified: SFT = “yeh format / yeh tone mein jawab do” sikhana; preference = “do plausible answers mein se better wala choose karna” sikhana.

Pitfall

“Fine-tuned” ko magic word maan lena. Fine-tune kis data aur kis objective se hua, woh product risk decide karta hai. Ek internal FAQ corpus par SFT se domain jargon improve ho sakta hai; safety refusals ya preference ranking usse automatically nahi aate. Jab vendor “instruction-tuned” kahe, poocho: SFT-only hai ya preference-optimized bhi?

3. RLHF — reward model + policy optimization

Reinforcement Learning from Human Feedback (RLHF) preference data ko explicit reward signal mein badalta hai. Typical pipeline (InstructGPT lineage): (1) SFT se starting policy banao; (2) humans ko same prompt ke multiple model outputs dikhao, unse ranking / comparison lo; (3) un comparisons se ek reward model train karo jo scalar score predict kare; (4) policy ko RL (often PPO) se update karo taaki high-reward answers generate kare, usually with a KL penalty toward a reference policy taaki model reward hack karke collapse na ho.

Yeh stack powerful hai aur operationally heavy bhi: reward model training, RL instability, hyperparameter sensitivity, aur “reward hacking” jahan model high score ke liye human intent se hat kar shortcuts seekh leti hai. Job-ready takeaway: jab koi system “RLHF-aligned” claim kare, aap samajh lo ke beech mein human (ya AI) preference labels the, ek learned reward tha, aur policy us reward ke against optimized hui — exact PPO recipe vendor-specific hoti hai.

Source

Long Ouyang et al., “Training language models to follow instructions with human feedback” (InstructGPT), arXiv:2203.02155, arxiv.org/abs/2203.02155. Paper describes fine-tuning GPT-3 with human demonstrations and preference rankings via a reward model, then optimizing the policy with reinforcement learning so the model better follows user instructions — reporting improved human preference win rates versus the base GPT-3 family on instruction-following evaluations.

4. DPO — preferences bina alag RL loop ke (intuition)

Direct Preference Optimization (DPO) preference learning ko ek classification- style objective mein rewrite karti hai. Idea: agar aap reward model aur RL step ko theoretically combine karo, to aap seedha policy parameters par ek loss likh sakte ho jo chosen response y_w ko rejected response y_l se prefer karaye, relative to a reference policy. Intuition form (lab isi ko toy scale par compute karega): beta-scaled difference of (policy log-prob minus reference log-prob) for chosen vs rejected, phir −log σ(·). Jab chosen ka advantage clear ho, loss chhoti; jab rejected zyada likely ho policy ke under, loss badi.

Simplified for this course: lab full DPO training loop nahi hai — na GPU, na tokenizer dump. Aapko given scalar log-prob sums (chosen / rejected, optional reference) se ek DPO-style loss term nikalna hai, taaki paper ka formula aapke hands mein numerical ho. Production teams DPO (aur variants) isliye pasand karti hain kyunki RL infra ka operational burden kam ho sakta hai; yeh claim context-dependent hai, silver bullet nahi.

Source

Rafael Rafailov et al., “Direct Preference Optimization: Your Language Model is Secretly a Reward Model,” arXiv:2305.18290, arxiv.org/abs/2305.18290. Authors derive a preference loss that optimizes the policy directly from preferred vs dispreferred completions relative to a reference model, avoiding an explicit reward-model fitting stage and a separate RL loop while targeting the same preference objective family as RLHF-style methods.

Hands-on · core-203 lab preview

Toy DPO term: δ = β · [(ℓ_θ(y_w) − ℓ_ref(y_w)) − (ℓ_θ(y_l) − ℓ_ref(y_l))], loss = −log σ(δ), jahan ℓ sequence log-prob sum hai. Agar reference logs zero rakho (teaching shortcut), margin chosen−rejected par collapse ho jaati hai. Yeh simplification lab docstring mein labeled hai — production DPO reference policy ko casually drop nahi karti.

5. Scaling laws — intuition only

Empirically, language-model loss predictably improve hoti hai jab aap model size, dataset size, aur compute ko scale karte ho — within the regimes papers ne measure kiye. Kaplan et al. ne early “scaling laws” curves popular kiye: loss as a power-law function of parameters / data / compute. Baad mein Chinchilla (Hoffmann et al.) ne emphasize kiya ki many large models undertrained on tokens the — optimal compute allocation mein data aur parameters dono ko balance karna padta hai, sirf parameters badhana kaafi nahi. Practitioner intuition: bigger often helps if you also feed enough data and pay the compute; “10× parameters” automatically “10× product quality” nahi hai, especially after SFT/preference stages aur eval mismatch.

Job-ready use: capacity planning meetings mein “scale the model” ko challenge karo with “scale which axis — params, tokens, or inference compute?” PROD track cost/latency se isse jodega; yahan aap sirf vocabulary lock kar rahe ho.

Source

Jordan Hoffmann et al., “Training Compute-Optimal Large Language Models” (Chinchilla), arXiv:2203.15556, arxiv.org/abs/2203.15556. Paper argues that for a fixed training compute budget, model size and training tokens should be scaled together; their analysis finds many prior large models were undertrained on tokens relative to an approximately compute-optimal allocation, and that smaller models trained on more data can outperform larger undertrained models on the same compute.

6. Context-window size — one checkpoint, then APP 303

Training aur architecture decide karti hain model ki maximum context-window size (kitne tokens ek forward pass mein legally attend ho sakte hain). Yeh number product copy mein “128k context” jaisa dikhta hai, lekin yeh applied memory strategy nahi hai: window ke andar kya rakhna hai, overflow par summarize / retrieve kaise karna hai, aur long-context cost kaise manage karni hai — woh APP 303 (context / memory engineering) ka scope hai. Yahan sirf itna yaad rakho: pretrain/fine-tune positional limits aur attention cost window size ko bound karte hain; engineering the contents of that window aage aata hai.

Intuition

C# service ka max request body size socho versus aapka API design jo us body mein kya bhejta hai. Window size = protocol limit. APP 303 = payload design (RAG, summaries, tool traces). Dono confuse mat karo.

Self-check · formative only

1. Pretraining loss FOUND 102 ke kis metric se map hota hai?

Reveal answer

Next-token negative log-likelihood — sequence / batch par mean NLL; perplexity exp(mean NLL) usi loss ka human-friendlier reporting scale hai.

2. SFT aur RLHF mein data / objective ka farq kya hai?

Reveal answer

SFT demonstration pairs par (usually) same next-token NLL use karti hai — “ideal” completions clone karna. RLHF preference comparisons se reward model seekhta hai, phir policy ko us reward ke against RL se update karta hai (KL-to-reference ke saath typical setups mein).

3. DPO RLHF se operational intuition mein kaise alag hai (course-level)?

Reveal answer

DPO preference pairs se seedha policy loss optimize karti hai — toy view mein alag reward-model + RL loop skip — chosen vs rejected log-probs (reference-relative) par −log σ(β · advantage) style term ke through. Full production recipes still careful with reference models and data quality.

4. Chinchilla-style scaling intuition ek line mein?

Reveal answer

Fixed compute budget par parameters aur training tokens dono ko scale karo; bada model with too few tokens undertrained reh sakta hai compared to a smaller model trained on more data.
